Section 00 — Foundation

The Calibration Engine

All thresholds, caps, baselines, and reference lines are computed from the venue's own settled shows — not set by a developer. Eight algorithms, each with a 4-tier fallback chain that degrades gracefully when data is sparse. A new venue gets useful estimates on day one. Full self-calibration is reached by show ~50.

Core principle: No number in this system is a constant. Every number is a query result. expense_cap is not $1,850 — it is PERCENTILE_CONT(0.75) ... WHERE venue_id=? AND bucket='$1–5K'. A venue where crews cost $600/show gets a $750 cap. One where crews cost $2,400 gets a $2,600 cap. The system learns both from data.

The 8 core algorithms

Algorithm 1 — Expense P75 per size bucket

Recal: on settleHigh when n≥8
The expense cap default for each gross bucket. Replaces every hardcoded cap constant. A Brooklyn jazz venue and a Nashville rock club will produce different values from this query — as they should. This number sets the default cap on any new deal in that bucket, and is the primary reference line on the live meter.
-- Compute P75 billed expense per bucket for this venue
-- Triggered after every settled show; stored in venue_calibration

WITH billed_by_show AS (
SELECT s.id AS show_id, SUM(e.amount) AS total_billed, classifyBucket(d.guarantee_amount) AS bucket FROM shows s JOIN deals d ON d.show_id = s.id JOIN expenses e ON e.show_id = s.id WHERE s.venue_id = :venue_id AND e.absorbed_by_venue = 0 AND s.status IN ('settled', 'closed') GROUP BY s.id, bucket )
SELECT bucket,
PERCENTILE_CONT(0.75) WITHIN GROUP (ORDER BY total_billed) AS p75_expense, PERCENTILE_CONT(0.50) WITHIN GROUP (ORDER BY total_billed) AS p50_expense, STDDEV(total_billed) AS expense_stddev, COUNT(*) AS n FROM billed_by_show GROUP BY bucket

-- n < 8 per bucket → use cross-venue P75 for same bucket class
-- n < 3 venues → use platform_defaults.expense_p75[bucket]
-- Store: venue_calibration (key='expense_p75_{bucket}', source, confidence, n)

Algorithm 2 — Hospitality cap

Recal: on settleMed when n≥5
Hospitality is the most-disputed expense category. Its cap must come from the venue's own data — a 300-cap club has different rider norms than a 1,500-cap theatre. A venue with a full green room will see numbers 3× higher than one with a fridge and a deli order policy. Cross-venue fallback uses capacity tier (small/mid/large), not city, as the grouping variable.
SELECT
PERCENTILE_CONT(0.75) WITHIN GROUP (ORDER BY hosp_total) AS hospitality_cap, AVG(hosp_total) AS hospitality_mean, COUNT(*) AS n FROM (
SELECT show_id, SUM(amount) AS hosp_total FROM expenses WHERE venue_id = :venue_id AND category = 'hospitality' AND absorbed_by_venue = 0 GROUP BY show_id HAVING SUM(amount) > 0 )

-- Cross-venue fallback groups by capacity_tier:
-- small (<300), mid (300-800), large (800+)
-- Capacity, not city, determines rider norms

Algorithm 3 — Genre P75 (venue-local blended with cross-venue)

Recal: nightlyHigh with cross-venue
Genre is the best predictor of expense level for first-time artists. A single venue rarely has enough shows per genre for a reliable P75 — cross-venue pooling solves this. When the venue has local genre data, it is blended with the platform estimate. The blend ratio shifts toward local data as local n grows: at n=5 (70/30 blend), at n=20+ (90/10 blend).
-- Tier 1: venue-local genre P75 (if n ≥ 5)
SELECT a.genre,
PERCENTILE_CONT(0.75) WITHIN GROUP (ORDER BY e.billed_total) AS p75_local, COUNT(*) AS n_local FROM expense_totals_per_show e
JOIN artists a ON a.id = e.artist_id
WHERE e.venue_id = :venue_id
GROUP BY a.genre

-- Tier 2: cross-venue pool (only billed_expense_total shared — no gross/payout)
SELECT genre,
PERCENTILE_CONT(0.75) WITHIN GROUP (ORDER BY billed_total) AS p75_platform, COUNT(DISTINCT venue_id) AS n_venues FROM platform_expense_pool GROUP BY genre

-- Blend rule:
-- n_local ≥ 5: BLEND(local_weight * p75_local + (1-local_weight) * p75_platform)
-- local_weight = MIN(0.9, 0.7 + (n_local - 5) * 0.025)
-- n_local < 5 and n_venues ≥ 3: p75_platform only
-- n_venues < 3: venue_calibration.expense_p75_{bucket} as proxy

Algorithm 4 — Dynamic breakeven gross per deal type & bucket

Recal: nightlyMed when n≥10
The breakeven gross is not a fixed number. It varies by deal type, by how expensive or lean a given artist's setup is, and by what the ticketing platform actually charges in fees. The engine computes it for every (deal_type × bucket) cell with sufficient data — giving each cell its own real breakeven line on the meter.
-- breakeven_gross = (avg_artist_payout + avg_billed_expense) / (1 - fee_rate)
WITH cell_stats AS (
SELECT d.deal_type, classifyBucket(d.guarantee_amount) AS bucket, AVG(s.total_to_artist) AS avg_artist, AVG(e.billed_total) AS avg_expense, AVG(tk.fees / NULLIF(tk.gross, 0)) AS actual_fee_rate, COUNT(*) AS n FROM settlements s JOIN deals d ON d.show_id = s.show_id JOIN expense_totals_per_show e ON e.show_id = s.show_id JOIN ticket_sales tk ON tk.show_id = s.show_id WHERE s.venue_id = :venue_id GROUP BY d.deal_type, bucket )
SELECT deal_type, bucket, n,
(avg_artist + avg_expense) / (1.0 - actual_fee_rate) AS breakeven_gross FROM cell_stats WHERE n >= 10

-- When n < 10: formula estimate
-- breakeven_est = (deal.guaranteeAmount + venue_avg_expense) / (1 - venue_fee_rate)

Algorithm 5 — Actual ticketing fee rate

Recal: monthlyStable after 10 shows
The SGP engine currently hardcodes 10% ticketing fees. In reality fee rates range from 6% to 15% depending on the ticketing platform and deal structure. High variance in the computed rate (stddev > 0.03) signals the venue uses multiple ticketing platforms — in which case the mode or most-recent rate is used rather than the mean.
SELECT
SUM(fees) / NULLIF(SUM(gross), 0) AS actual_fee_rate, STDDEV(fees / NULLIF(gross, 0)) AS fee_rate_variance, COUNT(DISTINCT show_id) AS n_shows FROM ticket_sales
WHERE venue_id = :venue_id
AND captured_at > NOW() - INTERVAL '12 months'

-- If fee_rate_variance > 0.03 → use MODE not AVG (mixed platforms)
-- Default if n < 10: 0.10 (10%)

Algorithm 6 — Dispute rate baseline per deal type

Recal: weeklyNeeds n≥20
The baseline dispute rate tells the system what "normal" looks like for each deal type at this specific venue. A spike above this baseline is the primary trigger for AI proactive alerts. For Stage 1–2 venues, platform-wide dispute rates by deal type are used — these are reliable because disputes correlate strongly with deal structure regardless of venue.
SELECT d.deal_type,
classifyBucket(d.guarantee_amount) AS bucket, COUNT(*) AS total_settled, SUM(CASE WHEN s.status = 'disputed' OR hasDisputedRecoup(s.recoups_json) THEN 1 ELSE 0 END) AS dispute_count, ROUND(dispute_count::numeric / NULLIF(total_settled, 0), 4) AS dispute_rate FROM settlements s JOIN deals d ON d.show_id = s.show_id
WHERE s.venue_id = :venue_id
AND s.completed_at > NOW() - INTERVAL '12 months'
GROUP BY d.deal_type, bucket HAVING COUNT(*) >= 20

Algorithm 7 — SGP accuracy drift (the self-improvement loop)

Recal: on settleNeeds n≥15
The engine closes its own feedback loop. After every settled show, it compares what the SGP suggested against what actually settled. Systematic drift above 15% signals the underlying P75s are miscalibrated — it triggers automatic re-runs of Algo 1 and Algo 3 for the affected cells. This is how the engine improves itself over time without human intervention.
SELECT d.deal_type,
AVG(g.suggested_price - s.total_to_artist) AS mean_delta, AVG(ABS(g.suggested_price - s.total_to_artist) / NULLIF(s.total_to_artist, 0)) AS mean_pct_error, COUNT(*) AS n FROM guarantee_suggestions g
JOIN settlements s ON s.show_id = g.show_id
JOIN deals d ON d.show_id = g.show_id
WHERE g.venue_id = :venue_id
AND s.completed_at > NOW() - INTERVAL '6 months'

-- mean_pct_error > 0.15 → trigger recalibration of Algo 1 + Algo 3
-- mean_delta consistently positive → suggestions too high (expense est too low)
-- mean_delta consistently negative → suggestions too low (expense est too high)

Algorithm 8 — Per-artist dynamic expense profile (recency-weighted)

Recal: on settleHigh after 2 shows
The most accurate single reference for any established act. Recency-weighted so that a crew change 2 years ago doesn't anchor the estimate. Cross-venue shows are included when available via the platform pool — this is the primary mechanism by which a touring artist's expense profile travels with them to a new venue.
WITH artist_history AS (
SELECT e.artist_id, e.show_id, e.billed_total, s.date, -- shows in last 12 months count 2x CASE WHEN s.date > NOW() - INTERVAL '12 months' THEN 2.0 ELSE 1.0 END AS recency_weight FROM expense_totals_per_show e JOIN shows s ON s.id = e.show_id -- Include cross-venue shows where shared via platform pool )
SELECT artist_id,
SUM(billed_total * recency_weight) / SUM(recency_weight) AS weighted_mean, MAX(billed_total) AS max_expense, STDDEV(billed_total) AS expense_stddev, COUNT(*) AS n_shows, COUNT(DISTINCT venue_id) AS n_venues FROM artist_history GROUP BY artist_id

-- weighted_mean → meter "artist avg" reference line
-- max_expense → suggested cap minimum (cap must be ≥ max seen)
-- expense_stddev → meter confidence band width

Section 01 — Monitoring Dimensions

What to Track

Four dimensions — per deal, per bucket, per genre, per period. Every threshold here references a computed value from the calibration engine, not a hardcoded number. The system defines "normal" from the venue's own data, then alerts when something departs from it.

Key shift: In the previous spec, "alert at 80% of $1,850" was a rule. In this version it is "alert at 80% of venue_calibration.expense_p75_1_5k." A venue where that field is $750 alerts at $600. One where it is $2,400 alerts at $1,920. The front-end renders the same component — the numbers it receives are different per venue.

Section 02 — Live Expense Meter

The Dynamic Live Meter

Every reference line is a live database query. The cap is the venue's computed P75 for this bucket. The artist average is the recency-weighted mean from Algo 8. The genre P75 is the blended local+platform estimate from Algo 3. All update after every settled show. The front-end renders whatever the API returns — zero business logic on the client.

Meter data contract: GET /api/shows/:id/meter returns a MeterPayload with every reference line, its source, its confidence, and the n backing it. alert_level is computed server-side. Confidence badges render from the payload fields — not from front-end logic.

Response rules:
- cap.confidence="low" → warn that cap is estimated, not venue-proven - maturity_stage < 3 → note baselines are still forming, add caveat - sgp_accuracy_pct > 15 → flag that recalibration is running - Never state a threshold as absolute → always cite its source and n

Settlement history: {positive_summary} | {negative_summary}
Prior disputes: {dispute_count} on {n_shows} shows
Why calibration state belongs in the prompt: The assistant must not say "your cap is $1,850" when it was actually computed from 3 cross-venue shows at low confidence. Including the source and n forces the model to qualify claims appropriately — turning calibration metadata into epistemic honesty rather than false precision.

Section 05 — Data Model

What to Store

One new table — venue_calibration — is the entire foundation. Everything else is derived from existing tables via the 8 algorithms. The calibration table stores every computed constant with its source, confidence level, backing n, and prior value for drift display.

CREATE TABLE venue_calibration (
id TEXT PRIMARY KEY, venue_id TEXT NOT NULL REFERENCES venues(id), < key TEXT NOT NULL, value REAL NOT NULL, value_p50 REAL, value_stddev REAL, n INTEGER NOT NULL, source TEXT NOT NULL, confidence TEXT NOT NULL, algorithm TEXT NOT NULL, computed_at INTEGER NOT NULL, prev_value REAL, prev_computed_at INTEGER, UNIQUE(venue_id, key) );
